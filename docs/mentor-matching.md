# 自愿引领匹配联调说明

## 已实现的规则

- 普通共勉使用 `mutual`；引领使用 `lead`，由申请接收方担任引领者。旧客户端不传模式时按 `mutual` 处理，旧关系迁移后保留为 `mutual`。
- 引领者需主动开启开关。近30天（含今天与29天前）至少24个有效打卡日，即近30天有效打卡率至少80%，且当前连续打卡至少7天。只统计审核通过、日期不晚于今天的记录；同一天多个目标只计一天。今天尚未打卡时，连续天数可从昨天往前计算。后端资格函数和候选SQL均显式检查24天、80%与7天。
- 引领者近30天有效打卡率必须严格高于申请人；等级不参与资格判断。申请人没有“低于80%”的限制，例如打卡率83.3%的引领者可以引领打卡率80%的申请人。
- 每名引领者最多3个待处理或已接受的引领申请。发送申请即占用名额，接受不会重复占位，拒绝、解除或拉黑会释放名额。普通共勉关系不占引领名额。
- 推荐、关键词搜索、详情和提交使用统一规则；发送和接受均会重新检查资格、开关、活动差异和名额。
- 关闭引领开关后停止接收新引领申请，已有搭子关系保留。已收到但尚未接受的引领申请继续占位，可拒绝以释放；重新满足条件并开启后方可接受。
- 引领关系解黑后不会自动恢复，需重新申请和校验，防止名额已释放后超额恢复。
- 修改关系使用 `READ_COMMITTED` 事务并按用户ID升序锁定双方用户行，覆盖重发、接受、拒绝、解除、拉黑与解黑。锁后重新读取申请状态，禁用相应查询缓存，避免读到锁前结果。

## 指标定义与论文表述

设统计日为数据库 `CURDATE()`，近30天窗口为 `[统计日−29天, 统计日]`。设 `D30(u)` 为用户在该窗口内审核通过的不同打卡日期数，则：

`R30(u) = ROUND(D30(u) × 100 / 30, 1)%`

分母固定为30，不使用注册天数、计划天数、任务数量或已提交的记录数。同一天多个目标审核通过只贡献一个有效日期；未来日期与未通过记录不计入。`S(u)` 为以今天为末日的连续有效打卡天数，今天尚未打卡时允许以昨天为末日；最近有效日期早于昨天时为0。

资格定义为 `E(u) = [D30(u) ≥ 24] ∧ [R30(u) ≥ 80%] ∧ [S(u) ≥ 7]`。在当前固定30天、整数日期计数的定义下，24天与80%等价，不是两种不同的活跃度指标；代码同时显式检查两项，使接口公布的门槛与执行条件一致。

可在论文中表述为：**系统采用固定30日滑动窗口统计审核通过且按日期去重的打卡行为。引领者须在窗口内至少完成24个有效打卡日（有效打卡率不低于80%），且当前连续有效打卡不少于7天。在此基础上，引领者须主动开启引领功能，其近30日有效打卡率严格高于申请人，并有剩余引领名额。发送申请和接受申请时，服务端均重新验证以上条件。**

| 引领者有效日 / 打卡率 / 连续天数 | 申请人打卡率 | 结果（假定开关已开启且有名额） |
| --- | --- | --- |
| 23 / 76.7% / 7 | 50% | 无引领资格 |
| 24 / 80% / 6 | 50% | 无引领资格 |
| 24 / 80% / 7 | 76.7% | 可以申请 |
| 24 / 80% / 7 | 80% | 有资格，但不能接受该申请人：必须严格高于 |
| 25 / 83.3% / 7 | 80% | 可以申请；申请人无需低于80% |

资格由 `MentorMatchingService.isEligible` 统一计算，SQL在推荐阶段先筛选同样门槛；小程序列表使用 `mentorEligible`、个人页使用 `eligible`，同时检查必需数据完整性。详情使用服务端 `leadAvailable`。客户端不再自行用24/80/7重算资格；界面可申请不替代服务端的提交、接受校验。

## 人工联调步骤

以下为此前准备的演示账号流程，需在具有对应账号和有效日期数据的本地测试环境执行；本次资格口径修复未连接数据库，也未重新生成测试数据。

1. 使用已准备的11号演示账号进入“我的”，在“让别人通过引领型找到我”卡片查看推荐状态、未达标原因、近30天有效打卡日、当前连续天数和名额，再开启引领匹配。历史准备的24天记录会随滑动窗口过期，应先核对当前统计。
2. 切换到打卡率低于该引领者的账号，在“搭子 → 匹配 → 引领型”中查找。例如引领者为24/30天（80%）时，申请人可用23/30天（76.7%）；相等的80%应被拒绝。若引领者为25/30天（83.3%），80%的申请人也可申请。可用“学习”目标筛选。旧测试数据会随滑动窗口变化，验收时以当前统计结果为准。
3. 从推荐卡片进入详情页，再发出引领申请；在11号账号收到的申请中检查“引领”标识并接受。
4. 双方“我的搭子”和详情页应保留引领关系标识；申请模式不会因进入详情而变成共勉。
5. 以其他账号继续申请，待处理和已接受合计达到3个时应停止推荐。旧页面继续提交时也会收到名额已满提示；拒绝或解除后恢复名额。
6. 关闭11号账号引领开关，已有搭子关系应保留，新引领申请应停止。可重新开启后继续验收。

## 接口字段

| 接口 | 契约 |
| --- | --- |
| `GET /api/user/mentor/status` | `enabled`、`eligible`、`approvedDays`、`checkinRate`、`streak`、`requiredDays=7`、`requiredApprovedDays=24`、`requiredRate=80`、`capacity=3`、`occupiedSlots`、`pendingCount`、`acceptedCount`、`remainingSlots`；新增 `recommendationState`、`recommendationAvailable`、`unmetRequirements` |
| `PUT /api/user/mentor` | JSON布尔值 `enabled`，返回最新状态；不接受字符串或数字冒充布尔值 |
| `GET /api/partner/match` | 参数 `goalType`、`keyword`、`matchMode`；候选返回 `mentorEnabled`、`mentorEligible`、`approvedDays`、`checkinRate`、`streak`、`remainingSlots` |
| `POST /api/partner/apply` | `partnerId`、可选 `goalId`、可选 `matchMode`；目标必须属于当前申请人且进行中 |
| `GET /api/partner/list`、`GET /api/partner/requests` | 每条关系或申请返回持久化的 `matchMode` |
| `GET /api/user/detail/{id}` | `mentorStatus`、`leadAvailable`、`leadUnavailableReason`、`relationMatchMode`，打卡率采用近30天口径 |

业务失败仍遵循现有 `{code,message,data}` 协议，小程序以 `code` 判断成功，不能只看HTTP状态码。

### 2026-11-10 引领推荐状态展示完善

“我的”页直接展示“让别人通过引领型找到我”卡片，开关表示参与意愿，推荐状态表示当前是否满足加入引领候选的条件。匹配页增加通往该卡片的入口，说明“引领型”用于寻找引领者；引领列表为空时提示调整筛选或尝试共勉型。

| `recommendationState` | 界面文案 | 条件（按表中顺序判断） |
| --- | --- | --- |
| `disabled` | 未开启引领推荐 | 开关关闭 |
| `ineligible` | 资格不足，暂停推荐 | 已开启，但24天/80%/当前连续7天至少一项未达到 |
| `full` | 名额已满，暂停推荐 | 已开启且达标，但待处理和已接受合计至少3个 |
| `available` | 可被引领推荐 | 已开启、达标且有剩余名额 |

`recommendationAvailable` 仅在 `available` 时为 `true`；`unmetRequirements` 返回所有未满足的资格条件，资格达标时为空数组。GET状态与PUT开关返回同一状态结构，原字段保持兼容。旧服务端缺少新字段时，小程序以原有资格与容量字段展示；容量未知时显示“推荐状态待确认”，不宣称可被推荐。

资格失效或名额已满时保留开启意愿；恢复资格且有名额后自动恢复参与推荐，页面再次进入或点击“刷新推荐状态”时更新。状态读取失败时清除旧结论并显示重试入口。可被推荐仍需符合对方打卡率、筛选、关系排除与排序条件，不保证每个账号都能看到。此次未改变24天/80%/7天和3个名额的规则，无数据库结构或业务数据变更。
