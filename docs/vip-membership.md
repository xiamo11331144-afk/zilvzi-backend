# VIP 引领申请与开发模拟开通

本功能只限制**发起新的引领型（`lead`）申请**。发起者必须有服务器确认的有效 VIP；接收者无需 VIP。共勉型（`mutual`）保持免费，免费用户可浏览引领匹配、接收和处理引领申请。VIP 不替代引领资格、活跃度、名额、目标归属、拉黑与审核规则。

有效期到期后，已发出的申请继续按原规则处理，已建立关系和打卡、消息等已有功能继续可用。会员只有一种固定期限套餐，无等级、试用、赠送、自动续费和退款流程。

## 数据库升级

先备份目标环境数据库并核对当前表结构，由部署者执行 `backend/sql/2026-11-07_vip_membership.sql`。本次开发**未连接实际数据库、未执行迁移**。

脚本只使用 `CREATE TABLE IF NOT EXISTS`，可对本功能首次升级重复执行，不删除或重建既有表，也不修改旧关系。新建：

- `vip_membership`：`user_id` 为主键/外键，`vip_until` 记录会员期限。无记录或期限为空即非会员，现有用户不会自动获得 VIP。
- `vip_order`：订单号唯一，保存本人身份、价格（分）、期限（天）、支付渠道快照、订单状态与创建/确认时间。

表为 InnoDB，以已有 `user.id` 为外键。若目标环境已经自行创建同名但不同结构的表，需先人工核对；`IF NOT EXISTS` 不会修复不同结构。基线 `backend/sql/zilvzi.sql` 含初始化语句，不应拿来覆盖已有库。本功能要求原匹配升级已经完成；旧库缺少 `mentor_enabled`/`match_mode` 时先核对原 `2026-11-07_mentor_matching_rules.sql`。

会员期限和订单时间按 **UTC** 写入；API 会员期限带 UTC 时区，小程序转换为北京时间显示。有效判断是 `vipUntil > 当前时间`，恰好等于截止时间即失效，不依赖小程序时钟或缓存会员标记。

## 配置

安全默认值不需要修改原有含凭据的配置文件。可通过独立环境配置或环境变量配置下列键：

| 配置键 | 默认值 | 含义 |
| --- | --- | --- |
| `vip.plan.duration-days` | `30` | 唯一套餐的固定期限，正整数天 |
| `vip.plan.price-fen` | `990` | 服务端订单金额快照，单位分；当前仅为测试示例，非正式售价 |
| `vip.payment.channel` | `disabled` | 当前只支持 `disabled` 或开发渠道 `mock` |
| `vip.mock-payment.enabled` | `false` | 显式允许模拟的额外开关 |

仅在开发测试环境使用以下配置示例：

```yaml
spring:
  profiles:
    active: dev
vip:
  plan:
    duration-days: 30
    price-fen: 990
  payment:
    channel: mock
  mock-payment:
    enabled: true
```

模拟可用须同时满足：渠道为 `mock`、显式开关为 `true`、至少一个活动 profile，且活动 profiles 全部属于 `dev`/`test`。默认 profile、未指定 profile、`production`/`prod` 或任何其他 profile 混入都会禁用。前端只展示服务器返回的模拟能力；直接请求确认接口也受同一检查。生产保持渠道 `disabled` 和开关 `false`。关闭模拟不会抹除数据库中已有会员期限；测试数据应使用独立环境。

## API 契约

所有路径均沿用登录拦截器和 `Authorization: Bearer ...`。身份来自认证请求属性 `userId`，请求体中的 `userId`、会员标记、金额、期限或支付成功断言不参与授权。响应沿用 `{code,message,data}`；业务错误可能使用 HTTP 200，调用方必须检查 `code`。

| 方法与路径 | 行为与关键返回字段 |
| --- | --- |
| `GET /api/vip/status` | 本人状态：`isVip`、`vipUntil`（带时区 ISO 时间或 `null`） |
| `GET /api/vip/plan` | `durationDays`、`priceFen`、`currency: CNY`、`paymentMode: mock/disabled`、`mockEnabled` |
| `POST /api/vip/orders` | 创建本人订单，无可信请求体；禁用环境拒绝创建不可支付订单 |
| `GET /api/vip/orders/{orderNo}` | 仅本人查询；不存在与不属于本人均返回同类不存在错误 |
| `POST /api/vip/orders/{orderNo}/mock-confirm` | 仅允许开发模拟且仅本人确认；不是任何真实支付的成功凭证 |
| `POST /api/partner/apply` | 保持原字段；新 `lead` 申请额外要求本人实时有效 VIP |

订单视图包括 `orderNo`、`status`、`paymentMode`、`priceFen`、`durationDays`。订单状态只有 `PENDING` 与 `TEST_CONFIRMED`；后者明确表示测试确认，并非真实付款。稳定申请权限错误为 `code: 40301, message: VIP_REQUIRED`，两个小程序申请入口据此提示会员页。其他主要业务错误沿用 `403`（模拟不可用）、`404`（订单不可见）、`409`（订单状态冲突）、`503`（下单渠道不可用），未登录使用现有 HTTP 401 流程。

## 一致性和恢复

模拟确认在同一数据库事务内执行条件订单状态更新和会员期限写入，并对本人用户行加锁、使用 `READ_COMMITTED`。同一订单重复确认不重复延长会员；同一用户不同订单串行读取最新期限，防止续期覆盖。未到期从原截止时间加套餐天数，已到期或未开通过从服务器当前 UTC 时间开始。任一写入失败应回滚整个事务。

订单保存创建时的服务端价格、期限与渠道；修改套餐配置不会篡改旧订单快照。当前模拟确认只接受模拟渠道订单。小程序不根据本地弹窗或按钮点击直接授予会员；只有确认接口完成后重新查询状态才显示结果。

会员页将创建和确认分成两步，支持取消、按钮忙碌保护、加载失败重试、查询当前订单。订单号在当前页面实例中保留，网络超时可重新查询或重复确认（后端幂等）；完全退出页面后订单仍保存在服务器，可通过本人订单查询 API 按订单号核对。暂未实现订单历史列表或自动恢复最近订单。返回原匹配场景后需主动再次点击申请，不自动发送申请。

## 验证与人工验收

可重复的离线检查：

```powershell
node scripts/prepare-vip-verification.cjs
node --test scripts/vip-miniprogram.test.cjs
$env:JAVA_HOME = '你的 Java 17 路径'
$env:MENTOR_DB_TESTS = 'false'
mvn -f .verification/vip-backend/pom.xml test
```

准备脚本以原后端 POM 为基础生成隔离 POM，源码仍指向原目录，构建与报告写入 `.verification/vip-backend/build/`，不覆盖 `backend/target/`。请勿启用 `MENTOR_DB_TESTS=true`：既有 MySQL 集成测试会连接本地实际数据库，并创建/删除其测试记录。本次默认关闭；它只隔离回归原匹配规则，不验证 VIP 数据库事务。

前端 Node 测试模拟小程序请求和页面事件，覆盖会员业务码、未登录、套餐禁用和异常、创建重复点击、取消与重复确认保护、超时恢复、确认后查状态及原场景返回。微信本地 `wcc`/`wcsc` 用于改动页面的 WXML/WXSS 编译；这不等同于开发者工具页面交互或真机验收。

本次实际测试数量与结果见本文件末尾的验证记录。仍需部署者在**独立测试库**升级后做 API/事务并发实测，以及微信开发者工具和真机的布局、导航、登录过期、弱网体验验收。重点场景：

1. 免费用户能共勉申请和浏览引领，发起新引领返回 `40301`。
2. VIP 通过原匹配规则后能申请；到期再发新申请被拒绝。
3. 非 VIP 引领者能收到、接受或拒绝原有效申请；申请者到期后审核仍按原匹配规则进行。
4. 旧搭子关系在到期后仍可查询、打卡和交互。
5. 未登录、他人订单、伪造字段、生产环境直接请求模拟确认均不能越权。
6. 同一订单并发确认只加一次，同一用户两笔订单并发确认累加两次；数据库失败不留下单边成功状态。

## 真实支付接入前需要的信息

当前没有真实下单、支付拉起、渠道查询或支付回调接口。正式接入前至少需要：

- 确定支付渠道/产品、正式价格与期限，以及商户和小程序的绑定方式。
- 对应商户号、AppID、渠道能力开通状态、测试与生产凭据、证书/签名密钥与证书轮换方式；凭据应由安全配置提供，不能提交到仓库或下发小程序。
- 渠道官方订单协议、金额/币种单位、订单超时规则、查询接口、支付状态和交易号语义。
- 可访问的 HTTPS 回调地址、验签/解密规范、回调重试规则、渠道交易号去重和金额/商户/应用/本人订单核对规则。
- 小程序支付权限、合法域名、支付拉起参数与用户标识获取方式，以及正式环境验收账号和流程。

真实会员生效必须由服务端可信渠道通知或主动查单确认。应新增渠道适配与回调验签，在已验证订单状态迁移的事务里复用会员续期原则；不能把当前本人可调用的模拟接口改名后用于真实支付，也不能将小程序支付回调作为唯一付款凭证。退款、自动续费等需另行明确需求。
